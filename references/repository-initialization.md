# 项目仓库初始化与既有结构

在已选定项目的连接检查或Work Sync前置读取发现仓库可能为空、分支不可读或结构缺失时使用。本流程复用project-context.md的项目/分支与github-connection.md的认证诊断；不创建仓库、不改授权、默认分支设置或本地profile。查询不要求先初始化；介绍功能不触发本流程。

## 只读识别，不用写入探测

1. 对明确目标使用get_file_contents列目标分支根目录；有可读提交即该分支已存在，记录提交SHA（非文件blob SHA）及路径类型。单个文件/records目录404不等于仓库空。
2. 如根目录失败且非明确认证/限流/网络错误，可对同一仓库省略ref读取默认分支根目录一次。默认分支可读而目标分支不可读表示目标分支待核对，不能宣布仓库空、静默切换或让push_files自动创建分支。默认分支读成功只证明可解析；不能凭省略ref或本地main配置推断其名称。
3. 当前MCP有只读仓库元数据/分支工具时，可核对同一仓库的default_branch及实际分支引用；元数据中的默认分支名称不证明引用已存在。没有这些工具不自动改白名单，以当前只读响应报告“默认分支名称/引用尚未确认”。
4. 只有明确GitHub返回empty repository/Git Repository is empty/This repository is empty等针对仓库的响应，或可信元数据加分支/提交证据证明无提交，才标为“空仓库、尚无可用分支”。HTTP 409本身、404、目录空列表、缺README、size=0、用户说新建均不能单独证明仓库空。仓库有提交但空树属于已初始化分支。
5. 401/403/404歧义、超时、无法完整读取时按github-connection.md诊断，状态为未知/受限，不生成可执行初始化写入；可继续保留本地草稿。用户核实页面状态仅作为补充，不冒充MCP实测。

## 沿用R7信息结构与当前兼容路径

| 路径 | 用途与兼容规则 |
| --- | --- |
| project.md | 项目名称、目标/范围、已确认阶段及协作/存储约定；只填有来源的信息，未知写待补充。不是成员个人profile或凭据文件 |
| records/<id>/record.md | 现有Markdown阶段记录，格式仍见record-format.md；旧顶层Markdown记录仍可查询，不迁移 |
| records/<id>/artifacts/<file> | 现有prepare-work-sync.py生成的该记录专属文本附件；相对路径从记录目录解析，不另复制到根artifacts |
| artifacts/ | 项目级共享/独立成果，现有引用继续有效；本轮不新增上传器，不强迫每条成果放两处 |
| links/ | 项目级共享外部成果链接说明；单条记录中的链接继续保留原位，不自动生成重复索引或下载外部内容 |

Git不保存空目录。初始化如需显式保留三目录，仅新增records/.gitkeep、artifacts/.gitkeep、links/.gitkeep（内容均空文本）；占位不是记录或成果。已有目录无需添加占位；README、.gitkeep等结构说明不纳入记录/成果统计。没有根artifacts/或links/不阻止使用已存在的记录内附件/链接，不作schema迁移，不修改R7的数据层级。

## 判断是否需要初始化

- 目标分支存在且已能按现有结构查询/同步：直接跳过，不为每次使用补模板。缺空目录会随首次文件提交自然产生，不能当同步障碍。
- 已有内容但缺project.md：提示“缺项目说明，现有记录仍可用”，用户可选择稍后补充；不强制初始化或重命名README。用户要求补齐时才预览仅新增的缺项。
- 既有project.md、目录说明或占位存在：保留；缺项列表来自完整最新读取。任何路径若是文件/符号链接/子模块而预期是目录，或project.md实际是目录，停止并说明冲突，不改类型、不跟随仓库外链接。
- 已确认空仓库：说明首次写入将建立分支/提交，展示初始化预览并等确认；只读成员可以查看方案，不能保证有写权限。
- 现有仓库但目标分支不存在：先核对是否选错分支，显式改绑定走V3.2预览；创建新分支是独立写操作，不混入初始化。

## 初始化预览（全部待批准）

明确项目名称、owner/repo、目标分支、远端已知状态、准备使用的工具、所有拟新增文件及完整内容、可能产生的额外文件/提交/分支。不猜成员名单、项目阶段或正式目标。最小project.md模板按已确认资料填充，例如：

```markdown
# <用户已确认的项目名称>

## 项目目标与范围
待补充（尚未提供正式说明）。

## 当前阶段
待补充，以实际阶段记录为准。

## 协作与存储
- project.md：项目说明。
- records/<id>/record.md：阶段工作记录。
- records/<id>/artifacts/：该记录关联的成果，不重复上传到根目录。
- artifacts/：项目级独立成果。
- links/：项目级外部成果链接；记录内链接保留原位。
- 记录先预览确认，再同步并回读核验；没有记录不等于没有开展工作。
```

该模板不是新的强制schema；已有说明格式照常读取。预览只含缺失项；空目录占位可包含在空仓库预览中，若用户选择按需生成目录则不提交占位。不自动增加README、license、.gitignore或其他工程文件。个人署名/profile和Token不复制到project.md。

## 写工具与首次提交边界

先发现当前可用MCP工具并核对实际参数/实现能力，不能用普通get_file_contents创建文件，也不能保证push_files在所有部署版本中支持空仓库。

- 若已授权的create_or_update_file可调用且支持该首次创建场景，可先创建已批准的project.md（创建不提供旧文件SHA），然后固定提交回读，再补已批准缺项；告知会有多次提交，按实际返回提交核验。不因有该工具就跳过路径存在性检查。
- 若使用push_files，官方公开源码当前会在空仓库先用Contents API创建空README.md和初始提交，再提交请求文件；目标非默认分支还可能创建分支。必须在预览中披露并获得对空README、实际初始分支、额外提交及目标文件的批准；不把一次工具调用称为原子单提交。源码不是当前Remote部署的行为实测，无法核实其初始化副作用/初始分支范围时不承诺精确写入，停在预览。
- 当前连接工具不足或无法核实首次提交能力时，保留方案与草稿；说明可由用户在GitHub网页按同一预览手动创建首个project.md，再由MCP只读回查并接续。不得默默改用Git CLI、REST直连、扩展工具白名单或另建仓库。任何工具配置调整需另行批准。

官方依据：[push_files实现](https://github.com/github/github-mcp-server/blob/main/pkg/github/repositories.go)、[空仓库初始化辅助函数](https://github.com/github/github-mcp-server/blob/main/pkg/github/repositories_helper.go)、[Contents API](https://docs.github.com/en/rest/repos/contents)。本轮不以源码/静态检查替代真实写入验收。

## 确认后检查、写入与回读

初始化确认不等于同步工作记录确认，反之亦然。只执行用户批准的具体目标、内容、文件及额外动作。写入前重新读取同一目标的最新状态，逐项核对拟创建路径及所有父路径；出现新文件、冲突、分支或状态变化时停止并刷新预览，不能覆盖。已存在且一致的文件跳过；若删去已存在项后提交计划/副作用变化，展示调整，不重做整份工作草稿。当前工具无原子“仅在不存在时创建”保障，存在检查与写入之间仍有竞争窗口；不能声称完全防并发覆盖，用户提示并发或观测到头变化时停止。

只写批准缺项；返回成功后按真实提交SHA固定回读所有初始化文件，逐字比较；核对目标分支根目录及工具可能生成的README/其他获批分支。没有完整回读前仅说“已提交、待核验”。出现部分写入、超时、分支创建后失败或未知状态时，先查远端实际状态及已产生的提交/文件，禁止盲目重试、删除回滚或重建仓库；修复需新的具体预览确认。结构齐备或已初始化后再次检查直接跳过，不重复提交占位。

## 接续Work Sync而不丢草稿

发现需初始化时，保留原packet文件、submission_id、request_key、request_fingerprint、created_at、record_content、附件字节/校验和，以及会话内已确认的仓库/分支/署名和批准范围；不重新提炼当前工作、不重建ID、不把初始化说明加入工作记录。没有草稿时可照旧生成一次再预览。

初始化核验完成后重新核对目标、草稿指纹和附件当前字节：
- 原工作草稿已得到明确批准且内容/目标/分支/署名/文件列表完全不变，且授权未被取消或限定“仅初始化”：继续原写入前查重，不要求重复确认同一工作正文。
- 原草稿仅已保存但未批准：直接展示原草稿并等待首次确认，不重新生成。
- 初始化批准本身从不批准上传工作；用户说“本次仅初始化”则停止并保留草稿。
- 项目、分支、署名、文件、附件字节或内容发生变化，或者用户已取消：按原Work Sync规则重新预览确认，不能借初始化绕过批准。

缺records/但根目录和目标分支可可靠读取时，确认其确实缺失后将该请求视为首条记录的查重基线；不因列records/的404中断所有同步，也不把认证/网络错误当不存在。其目录会随该次获批记录写入自然创建。之后回到work-sync.md原有查重、写入、固定提交回读流程。
